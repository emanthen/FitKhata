# Security Audit — 2026-10-11

Scope: static review per the H1 prompt (tenant isolation, IDOR, secrets,
dependency vulnerabilities, payment tampering, security headers). No load
testing or live penetration testing — Docker isn't available in this
environment, so this is code/config review plus the tools that run without
a live staging target (`pip-audit`, `pnpm audit`). `bandit`/`semgrep`/OWASP
ZAP were not run this pass — flagged as follow-up, not skipped silently.

## 1. Row-Level Security completeness — PASS

Every `TenantModel` subclass across every app was cross-referenced against
its app's migrations for a matching `ENABLE ROW LEVEL SECURITY` / `FORCE
ROW LEVEL SECURITY` / `CREATE POLICY ... USING (gym_id = ANY
(app_gym_ids()))` on its exact table name — not just migrations with "rls"
in the filename, every file in each app's `migrations/`.

**Result: 55/55 tenant tables have a correct policy, applied forward (not
just present in unreachable `reverse_sql`).** No app is missing RLS
entirely; no model fell through a gap between phases.

One thing worth knowing, not a finding: `attendance_attendance` is
partition-parent-only. An early migration also put RLS on its monthly
partitions directly; a later migration (`0003_fix_partition_rls.py`)
correctly reverted that, since Postgres only ever routes queries through
the parent table's policy — RLS on a partition directly, with no policy of
its own, would silently deny-all. `tests/rls/test_isolation.py` already
proves this is handled correctly.

Apps with no `TenantModel` subclasses (`accounts`, `gyms`, `saas`,
`publicapi`, `reports`, `core`) were confirmed to have an explicit comment
on each plain `models.Model` explaining why it's deliberately not
tenant-scoped (platform-level or org-level-only data, queried only under
`system_context()`).

## 2. IDOR review of `get_object_or_404` call sites — PASS

Every `get_object_or_404(...)` across the whole `apps/api` tree was
reviewed. ~15 call sites fetch a `Member`/`Organization`/`Gym`/`SaasInvoice`
by raw `pk` with **no** `gym=`/`org=` filter. Each one was traced
individually, not just pattern-matched:

- The large majority (attendance, billing's renewal family, coaching,
  notifications, members, retention) resolve `member_id` from a
  **cryptographically signed** pass-link token (`django.core.signing`,
  `MEMBER_PASS_SALT`) issued server-side — an attacker can't forge an
  arbitrary `member_id` without the signing key, so the missing explicit
  filter is not exploitable. All correctly run under `system_context()`
  since no gym is scoped yet at that point (same bootstrapping case as
  `register_gate_device`).
- `coaching.Exercise` lookups have no gym filter because `Exercise` is a
  global, non-tenant catalog by design (confirmed by the model's own
  "no tenant scoping" comment) — correct, not a gap.
- `members/views.py`'s `transfer` action looks up the destination `Gym` by
  raw `pk` with no org check at the view layer — **looked like a
  cross-tenant IDOR at first glance** (could a staff member move one of
  their own members into an unrelated org's gym?). Traced into
  `members.services.transfer_member`: it explicitly rejects with
  `ValueError` if `new_gym.org_id != member.org_id` before any write.
  **Not exploitable** — but the view doesn't catch that `ValueError`, so a
  malicious/mistaken cross-org transfer attempt currently 500s instead of
  a clean 400. Low-severity UX/error-handling issue, not a security hole;
  not fixed this pass (not a security bug, didn't want to touch
  error-handling behavior without being asked).
- `saas.views.ImpersonateView` looks up any `Organization` by `pk` with no
  further scoping — by design: it's gated behind `IsPlatformStaff`
  (`is_staff` + confirmed TOTP + optional IP allowlist), and impersonating
  arbitrary tenants is the entire point of that endpoint.

No exploitable IDOR found.

## 3. Secrets — one real finding, fixed

- No `.env*` files tracked in git (`.gitignore` correctly excludes them,
  only `.env.example` is tracked).
- `FIELD_ENCRYPTION_KEY` fails safe: an empty/missing value makes
  `Fernet("")` raise immediately on first use, so a misconfigured deploy
  crashes rather than silently encrypting with a weak key.
- **`SECRET_KEY` did not fail safe.** `config/settings/base.py` has
  `SECRET_KEY = env("DJANGO_SECRET_KEY", default="insecure-dev-key-change-me")`
  — a deliberate dev-convenience default so `make dev` needs no `.env`.
  `config/settings/prod.py` never overrode it, unlike `ALLOWED_HOSTS`
  (which already has no default and crashes if unset). A deployment that
  forgot to set `DJANGO_SECRET_KEY` would silently run in production with
  a secret key that's publicly visible in this very repo's history —
  compromising session signing and, more concretely here, the
  `django.core.signing`-based member-pass tokens section 2 just verified
  as safe (a leaked/default `SECRET_KEY` would let anyone forge a valid
  token for any `member_id`).
  **Fixed:** `prod.py` now requires `DJANGO_SECRET_KEY` with no default,
  same fail-fast pattern as `ALLOWED_HOSTS`.

## 4. Dependency vulnerabilities

- `pip-audit` (via `uvx`): **no known vulnerabilities** in any Python
  dependency.
- `pnpm audit`: 46 advisories. Breakdown and disposition:
  - **2 High — `sharp` (libheif + librsvg CVEs), installed at 0.33.5,
    patched at >=0.35.5.** `sharp` is used directly in `apps/bridge` for
    receipt-image rendering (runs in production on the gate PC) and
    transitively in `apps/web` via Next.js's built-in image optimizer,
    which processes member photo uploads — a real production exposure
    path, not just a dev tool. **Fixed:** bumped both to `^0.35.5`,
    reinstalled, re-verified `apps/bridge`'s receipt renderer still
    produces a valid PNG and the full bridge test suite (36/36) still
    passes.
  - **14 Critical — all in dev/build tooling only** (`orval`'s OpenAPI
    codegen, `vitest`'s UI server, `tinypool`). None run in any deployed
    service. `orval`'s RCEs require a malicious OpenAPI *input* — ours is
    self-generated by `drf-spectacular` from our own trusted code, not
    third-party input, so the realistic exploitability here is low, but
    the versions should still be bumped as routine maintenance. **Not
    fixed this pass** — flagged as a follow-up rather than silently
    dropped, since upgrading `orval`/`vitest` major versions risks
    breaking the codegen/test setup and deserves its own verification
    pass, not a rushed bump inside a security audit.
  - Remaining high/moderate/low findings are in Lighthouse CI's own
    dependency tree (`@lhci/cli` → puppeteer → `extract-zip`/`basic-ftp`)
    and ESLint's dependency tree (`braces` via `fast-glob`) — CI-only
    tooling, never deployed, not fixed this pass.

## 5. Payment tampering — already covered (verified, not new)

`billing/gateways/tests/test_esewa.py` and `test_khalti.py` already
exercise exactly the scenarios H1 asks for: a genuine signature pasted onto
a different claimed amount (`test_verify_rejects_a_tampered_signature`),
and equivalent coverage for Khalti. Confirmed these are real assertions
(`pytest.raises(GatewayVerificationFailed, match="signature")`), not just
tests that exist in name. Rule 6's idempotency (`transaction_uuid` unique +
`select_for_update`) was read directly in `billing.services.collect_payment`
earlier this session.

## Update: missed in this pass — eSewa receipt swap (CRITICAL)

Section 5 above checked that a *tampered* callback (a real signature
pasted onto an altered claim) is rejected, and confirmed that test is a
real assertion — both true, and both beside the point. The actual bug:
`EsewaGateway.verify()` never checked the callback blob's own
`transaction_uuid`/`total_amount` against the *specific* `Payment` row
the caller was asking it to confirm — only that the blob was internally
self-consistent (its embedded values matched its own signature) and that
eSewa's status API agreed with *those same blob-embedded values*. A
genuinely-signed callback from one's own completed NPR 10 payment could
be POSTed against a different `payment_id` for a pending NPR 19,990
payment, and `collect_payment()` would complete the large one — exploit
exists entirely within the application layer, no signature forgery
needed at all.

**Why section 5's own tests didn't catch it:** every existing test called
`EsewaGateway.verify({"data": data, "gym": gym})` with no `payment` in
scope at all — `verify()` didn't take one. There was no code path for a
test to even express "verify this blob against a *different* payment
than the one it's for," so the vulnerability was structurally invisible
to that test file regardless of how many tamper variations it covered.
H1's payment-tampering checklist item ("altered amount, altered
transaction_uuid, replayed callback, forged signature, wrong gym's
secret") doesn't name "right signature, wrong payment_id" as a distinct
category — this session is adding it as one, since eSewa's redirect-based
callback is exactly the shape that makes it reachable (Khalti and Fonepay
don't take client-supplied blobs the same way — confirmed safe, see
`fix/pilot-blockers`'s plan notes).

**Fixed:** `verify()` now takes the `Payment` object and rejects unless
the blob's `transaction_uuid`/`total_amount`/`product_code` match that
specific payment, before any status-check call; `check_status()` is then
called with the payment's own values, never the blob's. Also fixed in the
same pass: the response-signature formula was hardcoded to the request's
3-field list instead of building the message from the response's own
`signed_field_names` (eSewa's protocol makes the signed field set
self-describing specifically so it doesn't need to be assumed) — a
secondary structural issue in the same function, not a new vulnerability
class on its own, but worth fixing since it was sitting right next to the
real one. Regression tests: `test_verify_rejects_a_swapped_payment`,
`test_verify_rejects_an_amount_mismatch_against_the_payment`,
`test_verify_rejects_a_product_code_mismatch`,
`test_verify_uses_the_responses_own_signed_field_order` in
`billing/gateways/tests/test_esewa.py`.

## 6. Security headers (Caddyfile) — one real finding, fixed

HSTS with `preload`, `X-Frame-Options: DENY`, `X-Content-Type-Options:
nosniff`, `frame-ancestors 'none'`, `Server`/`X-Powered-By` stripped,
10MB request body cap — all already in place and correct.
`Content-Security-Policy`'s `script-src 'self'` has no `'unsafe-inline'`
(the thing H1 explicitly asks to verify) — confirmed correct.

**Found:** `Permissions-Policy: camera=(), microphone=(), geolocation=()`
blocks camera access for every origin, including same-origin — but the
gate kiosk PWA (same `DOMAIN_APP` deployment, Phase 3) needs
`getUserMedia()` for its QR scanner (`@zxing/browser`). This header would
have silently broken a core deployed feature the first time anyone tried
to use the kiosk's camera scanner against a real Caddy deployment (dev
server has no Caddy in front of it, so this would only surface in staging/
prod). **Fixed:** changed to `camera=(self)` — same-origin camera access
only; no third-party content is ever embedded on this domain, so this
doesn't weaken anything a real attacker could use.
